# Agents

Notes for AI coding agents working on this repository.

## Release management

Follow [RELEASING.md](RELEASING.md), with the `release` skill (`.claude/skills/release/SKILL.md`). On top of it:

- Only `origin/main` ships, through the release workflows. Never run `npm publish`, tag or create a GitHub release by hand: a failed release is resumed by rerunning the Release workflow.
- Never merge the refresh or version pull requests: the maintainer does.
- Don't mention unmerged branches or modules in the release notes.
- Agree on the version with the maintainer before running the Prepare workflow, and on the notes before marking the pull request ready.
- Build the "changes since" list from what was actually published: `release.js changes` warns when the last tag isn't the version on npm; then check the published tarball (`npm pack @hyperwatch/hyperwatch@<previous>`).

## Published address lists

Identities are checked against the address lists operators publish (`src/data/*-ips.json`).

- Lists published as structured data (JSON, plain text, one range per line) have a source in `src/data/ip-list-sources.json` and are refreshed by `node scripts/fetch-ips.js`, or by the Refresh workflow (`gh workflow run refresh.yml`), which opens the refresh pull request.
- Lists published only inside a page, a table or a PDF are copied by hand, listed in [RELEASING.md](RELEASING.md) ("Some lists have no updater"). Don't write a parser for them: a parser per page breaks silently when the page changes. To refresh them, read each source, update its file in the same format (a JSON array of ranges, single addresses as `/32` or `/128`), run `npx prettier --write src/data`, and report what was added and removed.
- A new operator list: if it is structured, add a source to `ip-list-sources.json`; otherwise copy it by hand, add it to the RELEASING.md list and to `handCopied` in `test/scripts/published-ips.js`.
- Before a release, refresh both kinds ([RELEASING.md](RELEASING.md), "Before you start: refresh the published ranges, keys and categories").

## Robot categories

The identity module sets `category` next to `identity`: the kind of robot the [robots database](https://github.com/hyperwatch/database) knows the request as (`src/lib/robot-category.js`, data in `src/data/robot-categories.json`).

- The file is generated by `node scripts/robot-categories.js <database checkout>` from the front matter of the database's robot files (`category`, `hyperwatch.identity`, `hyperwatch.family`). Never edit it by hand: fix the robot file in the database, then run the script.
- A category is a fact about a robot, not a judgement: Hyperwatch doesn't rank categories or pick "the most important" one. An identity whose robots differ has a category per agent family, and none for other families.
- The agent family only counts under the verified identity. Never look a category up by family alone: a request signed by one operator can send another's user agent.
- A new or renamed identity in `src/modules/identity.js` needs its robot file in the database (`hyperwatch.identity`) to get a category. `test/scripts/robot-categories.js` fails when the file names an identity the module no longer sets, and when a rule is written in a way `scanIdentities()` can't read.
- Before a release, refresh it: the Refresh workflow does ([RELEASING.md](RELEASING.md), "Before you start").

## Types

The sources are JavaScript with JSDoc types, checked by TypeScript (`checkJs`, `strict`): `npm run type:check` must pass, as in CI. Every parameter needs a type; `any` only for genuinely dynamic values (Immutable `getIn` values, parsed JSON, untyped packages), `catch (/** @type {any} */ err)` where the error's fields are read.

- Type options objects and anything public with JSDoc (`@param`, `@returns`, `@typedef`). Shared types (`Log`, `Config`, `ModuleConfig`, `Abortable`) are in `src/types.js`.
- `npm run types` generates the declarations the package publishes (`types/`, not committed; `prepack` runs it). `npm run types:test` packs the package, installs it in a temporary project with its dependencies only, and type-checks `test/types/consumer.ts` and every published declaration, strict and without `skipLibCheck`: add a line to `consumer.ts` when the public API changes, and an `@ts-expect-error` for what must be rejected.
- A class used as a type in another module must be exported by name (`module.exports.X = X`, or a `@typedef` next to `module.exports = { … }`): `import('./x').X` doesn't see classes in an object literal. A module exporting an instance (`pipeline.js`) exports its class's type with a `@typedef` (`Root`), and modules re-exporting it cast to that type, so the declarations refer to it instead of copying it.
- The published declarations may only refer to dependencies that ship their own types, Node's modules, and `@types/express`, an optional peer dependency (TypeScript users of Express have it). Nobody installs other `@types` because of Hyperwatch: declare the type in JSDoc instead (as `GeoipLookup` for geoip-lite, or the WebSocket input's `options` and `parse`). `types:test` fails when a declaration needs anything else.

## Web Bot Auth agents

The `webbotauth` module only fetches the key directories of the agents in `src/data/webbotauth-agents.json`. To add one, check that its directory answers with Ed25519 keys and that real signed requests verify, add it to the file, run `node scripts/fetch-webbotauth-keys.js <agent>`, and accept its verified signature in the robot's `identity` rule (`signedBy`).
