# Log

All log objects generated by the inputs and entering the pipeline must be [immutable maps](https://facebook.github.io/immutable-js/) which follow this specification.

## Log object

| Attribute | Type | Required? | Description                |
| --------- | ---- | --------- | -------------------------- |
| request   | Map  | yes       | A request map (see below)  |
| response  | Map  | yes       | A response map (see below) |

## Request object

| Attribute        | Type   | Required? | Description                                                                                    |
| ---------------- | ------ | --------- | ---------------------------------------------------------------------------------------------- |
| time             | string | yes       | When the web server received the request ([ISO-8601](https://en.wikipedia.org/wiki/ISO_8601)). |
| address          | string | yes       | IPv4 or IPv6 address (dotted notation)                                                         |
| method           | string | yes       | HTTP Method in uppercase: `"HEAD"`, `"GET"`, `"POST"`, ...                                     |
| url              | string | yes       | The relative URL (path + query string)                                                         |
| headers          | Map    | yes       | A collection of HTTP headers (string -> string)                                                |
| scheme           | string | no        | `"http"` or `"https"`                                                                          |
| protocol         | string | no        | `"HTTP/1.0"`, `"HTTP/1.1"`, or `"HTTP/2"`                                                      |
| port             | int    | no        | Default to `80` for `"http"` scheme and `443` for `"https"` scheme                             |
| captured_headers | array  | no        | List of headers the input had access to.                                                       |

**Note on `captured_headers`**

Ideally, the log clients forward all the HTTP headers and `captured_headers` does not need to be used.

However, when not all the headers are available, like in an `access.log` file for example, the client should indicate the list of headers that it has access to by listing their names in `captured_headers`.

This is useful for the pipeline to know whether a header is missing because it was not sent by the website visitor or because it was not available in the logs.

For example:

```javascript
{
  request: {
    captured_headers: ['user-agent', 'referer'],
  }
}
```

**Note on `headers`**

The name of the header must be lower-cased.

## Response object

| Attribute | Type    | Required? | Description                           |
| --------- | ------- | --------- | ------------------------------------- |
| status    | integer | yes       | The HTTP status code for the response |

## Route

`route` is the route pattern the request matched, in the application: `/v1/:collectiveSlug.json` for `/v1/babel.json?x=1`. It's set when the application knows it, so counting and filtering by route don't need a copy of the application's routes.

| Attribute | Type   | Required? | Description                                                                 |
| --------- | ------ | --------- | --------------------------------------------------------------------------- |
| route     | string | no        | The route pattern the request matched. Missing when no route matched (404s) |

The format, so that values from different applications compare:

- The pattern with `:name` for each parameter, as Express and path-to-regexp write it.
- A parameter that can only take a few fixed values keeps its value (`/v1/…`, `.json` / `.csv`, `members/all|users|organizations`), any other one shows its name: the number of values per application stays bounded.
- Literal segments lowercased, no trailing slash, no query string. `*` for a wildcard.
- No `route` when nothing matched, rather than a made-up value.

The [Express input](./input.md#express) sets it (see there), and an application can set its own. Inputs reading logs from another process keep a `route` the log has. `lib.route` writes values in this format:

| Function                       | Description                                                                                                                                                                                                                                                                               |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `normalize(route)`             | Lowercases the literal parts, drops the query string and the trailing slash                                                                                                                                                                                                               |
| `fromPattern(pattern, params)` | An Express pattern (`/:slug{.:format}`, `/files/*path`, Express 4's `/:format(json\|csv)?`), with the parameters the request matched: an optional part is kept when one of its parameters has a value                                                                                     |
| `fromRegExp(regexp, path)`     | A route declared as a regular expression, from the path it matched: a named group becomes `:name` (an unnamed one its number from 0), a group limited to fixed words keeps its value. `undefined` when the expression matches more than fixed text outside its groups (`/^\/files\/.*$/`) |
| `fromExpressRequest(req)`      | The route of an Express request (`req.baseUrl` and `req.route`), as the Express input reads it                                                                                                                                                                                            |

## Shared fields

Modules add their own fields to logs (`geoip`, `agent`, `identity`…). A few fields can come from more than one source. A specific source sets them first, by running earlier (a lower `priority`), and the generic one only fills what's still missing:

| Attribute     | Type   | Description                                                                                                                                                                                           |
| ------------- | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| address.value | string | The client address. Set by `cloudflare` (from `cf-connecting-ip`), filled by `address` from `request.address`                                                                                         |
| asn           | Map    | The autonomous system announcing the client address: `{ number, organization?, country? }`, only `number` required. Filled by `asn` from its table. Addresses no AS announces get no `asn`, never `0` |

A source that sets `asn` itself (e.g. from a CDN header) runs before `asn` (priority 501), and `asn` keeps its value.

## Address

What the modules add to a log, in `address`:

| Attribute | Type   | Description                                                                                                                                                                                                                                                                                                                                                           |
| --------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| value     | string | The client address (`address` module): the one set by an earlier module (`cloudflare`), else `request.address`                                                                                                                                                                                                                                                        |
| proxy     | string | `forward-proxy` module: when `value` is in the published egress ranges of a corporate web gateway, its name (`Zscaler`). Many organizations share these addresses                                                                                                                                                                                                     |
| forwarded | string | With `proxy`, the address the gateway forwards for: in `X-Forwarded-For`, the one just before the last occurrence of `value`, appended by the site's CDN (or the header's single entry, when the gateway connected directly: Zscaler replaces the header it receives). Zscaler writes the organization's public address there. A hint: `value` stays the verified one |

For `forward-proxy`, `X-Forwarded-For` from any other address is ignored: any client can write it. On `/addresses`, the `proxy` column shows the gateway and, in HTML, how many distinct addresses it forwarded for in the last 24 hours (`forwardedCount24h`, also a sort).
